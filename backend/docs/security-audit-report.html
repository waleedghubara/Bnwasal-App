كيف يعمل التطبيق ويتصل بالسيرفر بالآلية الأمنية الحالية

1. تشغيل التطبيق وفحص البيئة (Native RASP + FLAG_SECURE)

يبدأ الفحص على الفور في لغة الكوتلن الأصلية داخل كلاس MainActivity.kt قبل تحميل محرك Flutter. يتم التأكد من عدم وجود صلاحيات الروت أو أدوات التعديل، ويتم تفعيل FLAG_SECURE لحظر لقطات الشاشة أو البرامج الخبيثة التي تسجل الفيديو.

2. التوقيع الرقمي للطلبات (Request Signing & SSL Pinning)

عند إجراء أي طلب عبر شبكة HTTPS، يقوم كلاس dio_consumer.dart بمقارنة SHA-256 لبصمة شهادة الموقع، وتخلق الواجهة الأمامية توقيعاً رقمياً مخصصاً لكل طلب x-signature يعتمد على الزمن الفريد لمنع تكرار الطلب.

3. تدوير التوكنات (Refresh Token Rotation - RTR)

يتسلم الخادم طلب تحديث الوصول، ويقوم تلقائياً بتدمير توكن التحديث القديم وبناء توكن تحديث وتوكن وصول جديدين. في حال محاولة استخدام التوكن القديم مرة أخرى، يفترض الخادم حدوث اختراق ويلغي جميع الجلسات النشطة للمستخدم فوراً.

المرحلة الثامنة: محاكاة سيناريو هجوم على التطبيق

هذه المحاكاة تعكس سلوك مهاجم محترف حصل على ملف الـ APK الخاص بالإنتاج فقط وحاول استكشاف ثغرات النظام وتجاوز إجراءات الحماية:

الخطوة 1: محاولة تفكيك ملف الـ APK واستخراج الكود فشل الهجوم ❌
قام المهاجم باستخدام أداة apktool أو JADX-GUI لتفكيك التطبيق واستخراج الكود المصدري. وجد أن الكود البرمجي تم تصغيره وتعميته بنجاح بواسطة مترجم R8 وقواعد Proguard النشطة، كما تم إخفاء الروابط وعناوين خوادم الـ API خلف تشفير ApiCrypto المعمى.
الخطوة 2: محاولة التقاط صور للشاشة أو تسجيل الجلسات فشل الهجوم ❌
حاول المهاجم استخدام تطبيقات تصوير الشاشة أو تسجيل الفيديوهات أو توصيل الهاتف لعرض الشاشة عن بُعد بهدف سرقة أرقام البطاقة الوطنية أو بيانات الجلسة. واجه المهاجم شاشة سوداء تماماً بسبب تفعيل FLAG_SECURE في الكود الأصلي لـ MainActivity.kt.
الخطوة 3: محاولة استخدام توكن تحديث مسروق (Replay Refresh Token) فشل الهجوم ❌
حاول المهاجم استخدام توكن تحديث مسروق (Refresh Token) للحصول على توكن وصول جديد. نجح التطبيق في البداية بالدخول، ولكن بمجرد استخدام توكن التحديث مرة واحدة، يقوم الخادم بتدويره وتدمير التوكن القديم. وعند محاولة المهاجم إعادة إرسال التوكن القديم مرة أخرى، تكتشف الخوادم عملية إعادة الاستخدام (Reuse Attack)، وتقوم فوراً بمسح كل توكنات التحديث وتدمير كل جلسات المستخدم النشطة كإجراء احترازي.
الخطوة 4: محاولة اعتراض وتعديل طلبات الـ API عبر Burp Suite فشل الهجوم ❌
حاول المهاجم اعتراض البيانات للقيام بهجمة رجل في المنتصف (MITM) وتعديل قيم المعاملات والطلبات المرسلة. تم إجهاض الاتصال فوراً بسبب SSL Pinning، وحتى إذا نجح في تجاوز الـ Pinning عبر بيئة مهيأة، ترفض الخوادم الطلب لأن التوقيع الرقمي x-signature يعتمد على هويات الأجهزة والتوقيت الزمني الفريد x-timestamp ولا يمكن التلاعب بمحتواه دون معرفة السر المشفر.
